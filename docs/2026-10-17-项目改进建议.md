## 0. 一句话结论

项目完成度不低（5 库 21 表约 1.4 亿行入 Doris、4 套宽表、22 图 EDA、12 页作品集、全本地 Text-to-SQL RAG），但存在三类系统性问题：

1. **文档与实现脱节** — 7 份文档之间的数字互相矛盾，设计文档停留在"待实现"状态
2. **缺少验证与工程规范** — 无评测集、无测试、无依赖清单、无 .gitignore、无数据质量报告
3. **成果未被展示** — 最有含金量的 RAG 系统既没进作品集网站，也没开源

**建议只挑一件事先做：建 RAG 评测集。** 它是后续所有优化的决策依据，也是项目从"练手"变成"能写进简历并讲 10 分钟"的分水岭。

## 2. RAG 系统改进

### 2.1 建评测体系（最高优先级）

**问题**：`cli.py --bench` 只有 5 个问题，`benchmark()` 的判定标准是 `r["answer"] and not r["error"]`——**只判断"有没有回答"，不判断"答案对不对"**。SQL 跑通但口径算错，它照样报 `[OK]`。这意味着 5/5 通过不代表系统可用。

**方案**：

- [ ] 新建 `rag/evals/cases.yaml`，30-50 条评测用例，结构：

```yaml
- id: olist_gmv_total
  db: olist
  question: "olist 平台的 GMV 总额是多少"
  expected_sql: |
    SELECT SUM(price) FROM olist.olist_order_item_wide WHERE order_status = 'delivered'
  expected_value: 13591643.7   # 可选：标准答案
  tolerance: 0.01              # 相对误差容差
  tags: [aggregation, gmv]
```

- [ ] 新建 `rag/evals/run_eval.py`，输出四个指标：

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 执行成功率 | 生成的 SQL 在 Doris 上执行无错误的比例 | ≥ 90% |
| 结果准确率 | 有 `expected_value` 的用例中，结果在容差内的比例 | ≥ 75% |
| P50 / P95 延迟 | 端到端耗时分位 | P50 ≤ 15s，P95 ≤ 40s |
| 平均重试次数 | `SQL_MAX_RETRIES` 的实际消耗 | ≤ 0.5 |

- [ ] 评测报告输出到 `docs/benchmark/2026-10-xx.md`（含失败用例明细）
- [ ] 覆盖度要求：5 个库**每个至少 6 题**，难度分三档（单表聚合 / 多条件过滤 / 分组排序 TOP-N）

> 有了评测集，改 prompt、换模型、调 top_k 才有决策依据，而不是靠"感觉变快了"。

### 2.2 提升检索质量（准确率性价比最高的一改）

**问题 1：知识库只覆盖 21 张表中的 5 张**

`schema_extractor.get_wide_tables()` 的逻辑是"优先取表名含 `wide` 的表，否则取该库第一张表"，等于每个库只抽一张表，丢弃了 16 张。README 记录知识库仅 **118 条文档**，覆盖严重不足。

- [ ] 改为抽取全部 21 张表的元数据
- [ ] 每张表追加统计元数据（模型很吃这类信息）：行数、更新时间、分区键、是否是宽表
- [ ] 表级文档增加"表类型"标签（原始表 / 宽表），prompt 中优先推荐宽表

**问题 2：混合检索没有分层**

`retrieve_context()` 把表级、字段级、示例、业务知识四类文档混在一个 top-6 里捞，字段级碎片（数量最多）容易把表级文档挤掉，导致模型看不到完整表结构。

- [ ] 三级检索改造：
  1. **库路由**：先判定问题属于哪个库（关键词匹配即可，如问题含"淘宝/PV/加购"→ taobao），失败则退化为全库
  2. **表级保底注入**：命中的库，其表结构摘要强制放入上下文（不占 top_k 名额）
  3. **库内 top-k**：再检索字段级 / 示例 SQL / 业务知识
- [ ] 可选：`BAAI/bge-reranker-base` 对 top-20 重排取 top-6（CPU 可接受）

**问题 3：两个库没有示例 SQL**

`EXAMPLE_SQL_TEMPLATES`（knowledge_builder.py:15-27）只覆盖 olist / taobao / amazon，**instacart 和 product_samples 一个示例都没有**，这两库准确率大概率明显偏低。

- [ ] 每库补齐 3-5 组"问题 → SQL"，从现有 EDA 脚本（`11_olist_eda.py`、`10_taobao_eda_pyspark.py` 等）提炼
- [ ] instacart 重点：复购率、热销商品、加购顺序、部门维度的订单分布
- [ ] product_samples 重点：价格分布、店铺维度统计、评论数 TOP-N

**问题 4：知识库无增量刷新**

`rebuild()` 每次都 `delete_collection()` 全量重建。

- [ ] 增加 schema 指纹（对 `extract_all()` 结果取 hash），存到 `models/chroma_db/schema_fingerprint.json`
- [ ] 启动时比对，仅在变更时重建，否则跳过（省去每次启动约 100MB 嵌入模型加载 + 全量写入）

### 2.3 SQL 安全校验改为白名单（安全组件，P1）

`sql_validator.py` 用黑名单正则，已可枚举出的失效场景：

| 场景 | 现状 | 后果 |
|------|------|------|
| `WHERE title = 'update'` | `_FORBIDDEN.search` 不剥离字符串字面量 | 正常查询被误拒 |
| `LIMIT 10, 20` | `\blimit\s+\d+` 匹配不到逗号形式 | 追加 `LIMIT 1000` → 语法错误 |
| `WITH cte AS (...) SELECT` | `^select` 判定失败 | CTE 查询被拒，而复杂分析几乎离不开 CTE |
| `SELECT SLEEP(10)` | 不在黑名单中 | 无法防资源耗尽型攻击 |
| 未知绕过手法 | 黑名单天然不全 | 存在理论注入风险 |

**方案**：

- [ ] 引入 `sqlglot`，改为 **AST 白名单解析**：
  - 根节点必须是 `Select`（自动放行 CTE）
  - 遍历 AST，只允许 `Select / Where / Group / Order / Limit / Join` 等只读节点
  - 校验表名必须带库前缀且在 `config.DORIS_DATABASES` 白名单内
  - 限制单条 SQL 的扫描表数（如 ≤ 3）
- [ ] 字符串字面量剥离后再做关键字扫描（保留一道正则兜底）
- [ ] 补充 LIMIT 判定：支持 `LIMIT n`、`LIMIT n, m`、`LIMIT n OFFSET m` 三种形式
- [ ] **配 Doris 只读账号做双保险**（见 §4.1）——代码层校验永远不该是唯一防线

- [ ] 既用于调 prompt / 定位失败，也可作为"系统可观测"的作品集素材
- [ ] Streamlit 侧加一个「调试信息」折叠面板展示本轮日志

### 2.5 性能与体验（P2）

**缓存**：

- [ ] 问题级缓存（SQLite 或简单 dict + TTL），键 = 问题归一化后的字符串
- [ ] `COUNT(*)`、总行数、GMV 总额这类高频问题会反复触发亿级表扫描，缓存收益最直接
- [ ] 命中缓存时界面标注"（缓存结果，{时间} 生成）"

**亿级表保护**：

- [ ] taobao 1 亿行，模型极易生成无过滤的 `COUNT(DISTINCT user_id)` 把 BE 打满
- [ ] 方案 A（推荐）：建预聚合 ads 表，RAG 优先查聚合表
- [ ] 方案 B：prompt 中对 taobao 强制注入"必须带时间范围或类目过滤"，校验器对 taobao 无 WHERE 的查询降级警告
- [ ] 方案 C：利用 §2.4 的日志，统计慢查询 TOP-N，针对性建 rollup / 物化视图

**回答可读性**：

- [ ] 删除 LLM 解读层换来了速度，但回答退化成裸表格（`format_answer` 只做 `df.head(20).to_string()`）
- [ ] 加**规则化模板解读**（零推理开销）：
  - 单值结果 → "olist 平台 GMV 总额为 13,591,643.70"
  - 时间序列 → "从 2016-09 到 2018-08，GMV 由 X 增长到 Y，峰值出现在 2017-11"
  - TOP-N → "TOP3 分别为 A、B、C"
- [ ] Streamlit 加开关：「启用深度自然语言解读」（勾选才调 LLM，默认关）

**流式输出**：

- [ ] SQL 生成阶段启用 `ChatOllama` streaming，或至少分阶段进度提示（检索完成 → SQL 生成中 → 执行中），缓解 15-40s 的空白等待
